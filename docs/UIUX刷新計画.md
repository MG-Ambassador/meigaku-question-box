# 明学の質問箱 UI/UX刷新計画

作成日：2026-09-25　状態：設計提案・実装前

## 1. 目指す体験

**開いたらすぐ質問でき、指の動きに応え、安心して送信を終えられる。運営は、読んでいる場所を失わずに新しい質問を受け取れる。**

最優先は操作感。押した手応え、反応の速さ、操作結果の確かさ、失敗からの戻りやすさを一つの品質として設計する。シンプルさ、直感性、明確なフロー、既存カラーの維持、スマートフォンでの自然な操作、イベント中の利用、共有のしやすさを、この品質につなげる。

「スマートフォンネイティブ」は、今回の計画ではスマートフォンで自然に使えるWeb体験と解釈する。GitHub Pages＋Cloud Run＋Firestore、匿名投稿、運営のGoogle認証を維持する。専用iOS/Androidアプリの開発は別の判断とする。

対象は来場者画面と運営画面。質問本文の閲覧は運営に限り、回答はイベントで行う現行のサービス範囲を維持する。共有する対象はイベントの募集ページ。質問本文・運営画面の共有機能は追加しない。

## 3. 現状と変更方針

| 現状・根拠 | 利用時の課題仮説 | 刷新方針 |
|---|---|---|
| 来場者画面は大きなヒーロー、説明、装飾のQ、別ダイアログ内のフォーム／`app/page.tsx` | 会場で質問したいとき、入力に至るまでの情報が多い | イベント名と本文入力を最初の画面に置く |
| 投稿入口がヘッダーとヒーローにある | 同じ操作の重複。ヘッダー側は受付状態による無効化がない | 主操作を1つに集約し、受付状態と同期する |
| ボタン全体にhover時の上移動があり、共通の押下表現がない／`app/globals.css` | タッチの押し込みと、マウスの浮き上がりが整理されていない | 通常・押下・復帰・待機・完了を共通仕様にする |
| 成功と失敗を同じ `message` と `role="status"` に表示 | 送信完了と入力継続の境界が弱い | 完了画面と入力中のエラーを分ける |
| 公開イベント取得失敗はconsole出力のみ。URLのeventを一覧で見つけられない場合の表示も曖昧 | 障害、終了、存在しないURLが「準備中」に見えうる | 単一イベントAPIで、終了・404・通信失敗を区別する |
| 運営は設定→分析→質問一覧の縦長構成／`app/admin/panel.tsx` | 会場で最も使う質問一覧まで遠い | 「質問」「集計」「設定」を分け、質問を初期表示 |
| 更新は手動。取得時に一覧を空にしてloading表示 | 最新を見逃しやすく、更新のたび読書位置を失いやすい | 自動で新着を検知し、利用者の操作で一覧に反映する |
| サーバーは `nextCursor` を返すが、クライアントはcursorを送らず、画面にも追加読込がない | 最初の50件より前の質問に到達できない | スナップショットを保つ「さらに読み込む」を実装する |
| 投稿APIクライアントは呼出ごとにrequestIdを生成／`lib/api-client.ts` | 保存後の応答だけ失われた場合、手動再送で重複しうる | 同じ送信の再試行では同じIDと内容を保持する |
| 募集URLは常に `from=instagram`／`lib/public-url.ts` | 一般共有もInstagram経由として集計される | 通常共有とInstagram掲載用リンクを分ける |
| イベント編集はPOSTで、既存のversion付きPATCHを利用していない | 複数担当者の編集競合を利用者に伝えられない | 編集はPATCH＋versionを使い、競合時に差分を確認できるようにする |

優先度は、P0＝入力消失・重複送信・誤操作・操作への反応、P1＝フローと当日運用、P2＝細部の仕上げ。見た目の調整だけで完了としない。

## 4. 情報設計と画面構成

### 来場者：イベント → 入力 → 完了 → 任意の共有

```text
イベント付きURL / QR
  → 対象イベントを確認して入力画面
  → 本文を書く・テーマを選ぶ
  → 質問を送る
      → 成功：完了画面 → もう1件質問する / この質問箱を共有
      → 失敗：入力を保持 → 理由を確認 → 再試行

イベント指定なし
  → 受付中が1件：そのイベントの入力画面（対象名は常に表示）
  → 複数：イベントを選ぶ → 入力画面
  → 0件：受付中のイベントがないことを表示
```

URL指定がある場合は別イベントに自動で振り替えない。終了していれば終了表示、存在しなければリンク確認の案内、通信失敗なら再読込を表示する。

**入力画面の構成案**

```text
明学の質問箱                         使い方

イベント名                           変更
開催情報                             受付中

聞いてみたいこと
┌──────────────────────────┐
│ 質問本文の入力欄                     │
│                                      │
└──────────────────────────┘
氏名や連絡先は書かないでください。    0 / 500

テーマ
［大学生活］［学び・授業］［入試・進路］
［留学・国際交流］［その他］

名前・ログインは不要です。
運営が確認し、イベントで紹介する場合があります。
すべての質問に回答できるとは限りません。

［                 質問を送る                 ］
```

- 本文を最初の入力にする。テーマは5択のラジオ型チップで全選択肢を見せる。新しいカテゴリは増やさず、初期案は現行の「大学生活」を選択済みにする。誤分類が多い場合はテスト結果を基に見直す。
- ラベルはプレースホルダーで代用しない。入力例は1つにとどめる。
- 入力は現行契約のtrim後1〜500に合わせる。絵文字を含む文字数の数え方をAPIと統一する。旧ロードマップの「5〜500」との記述差も実装時に解消する。
- 主ボタンは入力内容の近く、親指で届く下部に置く。狭い画面で固定・追従する場合も本文・同意説明・キーボードと重ならないことを優先する。
- 下部の安全領域は `env(safe-area-inset-bottom)` を考慮し、画面高は `100dvh` を基本に実機で確認する。キーボード表示時の可視領域に応じて追従を解除できるようにし、ブラウザー標準の戻る・スクロール・ピンチ拡大を妨げない。
- キーボードは本文をタップして開く。初回表示で自動表示して画面を狭めない。日本語IMEの確定や本文のEnterで送信しない。
- 入力中にイベントを変更する場合、下書きをイベント単位で保持し、別イベントへ本文を自動転用しない。
- 使い方と詳細な利用案内は補助シートに集約する。名前・ログイン不要、閲覧範囲、紹介の可能性など投稿判断に必要な説明は入力画面に残す。

**完了画面の構成案**

```text
           ✓
     質問を受け付けました
運営が確認し、イベントで紹介する場合があります。

［            もう1件質問する            ］
          この質問箱を共有する
```

完了はサーバーの成功応答後に確定する。完了表示は自動で閉じない。完了見出しにフォーカスを移し、読み上げでも送信結果を認識できるようにする。入力のクリアは成功した本文だけに適用し、次の入力を先行して消さない。

### 運営：質問を読むことを中心にする

スマートフォンは下部に「質問・集計・設定」の3つの移動先を設ける。PCでは同じ情報構造を上部またはサイドに置く。イベント選択と受付状態は共通ヘッダーに置き、ログイン中の担当者・ログアウトはアカウントメニューにまとめる。

| 画面 | 最初に見せるもの | 主操作 |
|---|---|---|
| 質問 | イベント名、更新状態、新着案内、質問本文 | 新着を表示／さらに読み込む |
| 集計 | 質問総数、テーマ別、流入元、日別、集計時点 | 集計を確認する |
| 設定 | イベント名・開催情報、受付状態、募集リンク | 保存する／共有する |

質問一覧は本文を16〜18pxで読みやすくし、テーマ・時刻・流入元を補助情報にする。装飾のための大きなカード余白を減らす。質問の回答済み管理、公開、いいね等は今回追加しない。

受付停止は会場全体に影響するため、対象イベントを明記して確認する。投稿送信やリンクコピーには確認ダイアログを挟まない。設定の409競合時は編集内容を保持し、最新情報と照合して保存し直す。

既存の `/`、`/admin/` と `?event=` を入口として維持する。タブ状態はURLまたは履歴で復元できるようにし、ブラウザーの戻る操作で予期せずログイン前に戻らない設計にする。

## 5. 最優先：操作感の仕様案

### 押す → 沈む → 戻る → 結果が分かる

下記は試作の開始値。全画面実装の前に、実機で自然さと速度を確認して確定する。

| 状態・操作 | 見た目と動き | 時間の初期案 | 振る舞い |
|---|---|---|---|
| ボタンに触れる | 表面を1px沈め、scale 0.98、薄い影を縮める | 80〜100ms | 通信を待たず即時に反応 |
| 指を離す | 通常の位置・大きさへ戻る | 140〜180ms | 大きく弾ませない。処理はアニメーション完了を待たず開始 |
| 指が外れる・スクロールに移る | 押下状態を解除 | 100ms以内 | pointercancelを扱い、送信しない |
| テーマの選択 | 輪郭・塗り・チェックで選択を示す | 100〜140ms | 位置やサイズを変えず、他の項目を押しやすいままにする |
| 補助シートを開く | 下から短く出現、背景を薄く暗くする | 220〜280ms | 閉じるボタンを用意。フォーカスを内部へ移す |
| 送信中 | 同じボタン幅で「送信中…」と進行表示 | 状態変更は即時 | 二重送信を防止。フォーム高さを変えない |
| 送信成功 | チェックと完了文を表示 | 180〜240ms | 1回だけ。自動遷移・紙吹雪・音は使わない |
| コピー成功 | ボタン文言とチェックを一時変更 | 100〜140ms | 「コピーしました」。画面下だけの通知に依存しない |
| 新着検知 | 「新しい質問がN件」を表示 | 120〜160ms | 読んでいる本文を動かさない |
| エラー | 該当箇所に理由と回復操作 | 即時 | 強い揺れで注意を引かない |

操作への視覚的反応は100ms以内を目標とし、操作全体の応答時間は別に測る。送信成功を演出するための人工的な待ち時間は設けない。通常の状態切替は `cubic-bezier(0.2, 0, 0, 1)` を開始値とし、押下は素早く、復帰はわずかに穏やかにする。

実装ではネイティブのbuttonとclick/submitを主軸にし、pointerdownは視覚反応に限定する。Space/Enterからも同じ結果を得られるようにする。視覚面だけを変形し、タップ判定領域は縮めない。hoverの動きはマウス対応環境に限定し、現在の全ボタン共通の上移動と競合させない。

### 触覚・動きを減らす設定

Webの振動はブラウザー・端末依存のため、必須条件にしない。初期版は視覚的な押し込みと即時反応で手応えを成立させる。対応端末での短い振動は実機評価後の任意拡張とし、振動がない端末でも同じ情報を伝える。[MDN Vibration API](https://developer.mozilla.org/en-US/docs/Web/API/Vibration_API)

`prefers-reduced-motion` では移動・拡縮・バネ表現を停止し、輪郭・塗り・文言の即時切替にする。現行CSSのtransition停止に加えてkeyframe animationも対象とする。待機は静止アイコンと文言でも分かるようにする。操作に伴う動きを無効にできる設計はWCAGの考え方にも沿う。[W3C Animation from Interactions](https://www.w3.org/WAI/WCAG22/Understanding/animation-from-interactions.html)

## 6. カラーを維持した視覚設計

色値を変えず、面積・役割・組み合わせを整理する。画面全体の黄色を減らしても、主要アクションと小さなブランド表現に既存の黄色を残す。

| 用途 | 現行色 | 方針 |
|---|---|---|
| ブランド・主要操作 | `#ffdf00` | 主ボタン、選択状態の一部、ブランドの印に使用 |
| 本文・黄色上の文字 | `#20211f` / `#171717` | 既存の濃色を使用。役割を整理してトークンに集約 |
| ページ背景 | `#fbfbf8` | 維持 |
| 入力面・シート | `#ffffff` | 維持 |
| 境界・補助情報 | `#e5e5e5`、既存のグレー類 | 装飾用と操作に必要な輪郭を区別 |
| エラー | `#e7000b` 等の既存エラー色 | 文言・アイコンと併用。色だけで判断させない |
| 運営の背景・ヘッダー | `#f1f3f4` / `#202521` | 来場者画面との区別を維持 |

`--primary` は黄色だが `--primary-foreground` は現在 `#fafafa`。現在の手書き `.primary` は黒背景・白文字なので、トークンと実際の主ボタンも一致していない。共通化時には黄色のボタンへ既存の濃色文字を割り当て、黄色上の白文字を避ける。薄い境界色だけを入力欄の唯一の識別手段にしない。

寸法は4/8px基準、本文16px以上、常用ラベル14px以上、見出し24〜28pxを開始値とする。主ボタン高は56px、その他の操作領域も原則48×48 CSS px以上。角丸は入力・ボタン12px、シート20pxを初期案とする。文字拡大時は固定高を強制しない。

48pxは今回の使いやすさの設計目標。WCAG 2.2 AAのTarget Size Minimumは原則24×24 CSS pxで例外条件があり、両者を混同しない。[W3C Target Size Minimum](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)

本文・操作ラベルのコントラスト、フォーカスの視認性、読み上げ順を確認する。色の追加で解決する前に、既存の濃色、文字の太さ、輪郭で改善する。日本語システムフォントを基本にし、フォント読込が操作開始を遅らせないようにする。

## 7. リアルタイム利用と通信状態

### 運営の自動更新

初期案は、表示中の「質問」画面で3秒間隔のポーリングを行う準リアルタイム方式。表示は「自動更新」とし、正常通信下で投稿の保存から新着案内まで95%が5秒以内を目標に検証する。実測で不足する場合にSSE等の配信方式を比較する。ブラウザーからFirestoreへ直接接続する構成には変更しない。

1. 初回は最新50件と集計を読み、一覧のスナップショットを確定する。
2. 定期確認は既存APIの `pageSize=1` で開始し、最新sequence・総数等を確認する。次の取得は前の取得完了後に予約し、同時リクエストを重ねない。
3. 読んでいる一覧とスクロール位置を維持したまま、新着数を案内する。読み上げはまとめて行い、毎回割り込ませない。
4. 「新しい質問を表示」を押したとき、最新の先頭ページを読み、古いページのcursorをリセットする。質問IDで重複を排除する。新着が50件を超えても「さらに読み込む」で辿れるようにする。
5. 過去ページの取得には初回スナップショットのcursorを使う。新着確認の集計と過去ページの集計を同じ時点の数字として混在させない。
6. 10分のcursor期限や保守による失効時は、読んでいた内容を残して「一覧を更新」を案内する。自動的に先頭へ戻さない。

非表示タブ・画面ロック・オフライン時は定期取得を停止し、復帰時に再取得する。エラー時は6→12→30秒を目安に間隔を延ばし、最終成功時刻と「更新できていません」を表示する。通信が失敗しても取得済み本文を空にしない。イベント切替・ログアウト後の古い応答は破棄する。

集計画面は初期案15秒間隔＋手動更新、設定画面は必要時の取得とする。公開画面は表示時・復帰時と、受付状態確認の30秒間隔を開始値にする。実際の投稿可否は送信時のサーバー判定を最終とする。

3秒間隔で運営5人が2時間表示した場合、通信時間を無視した上限側の概算は12,000リクエスト。stats 1件と質問最大2件を各回取得すると、文書取得は最大約36,000件相当になる。課金総量の見積もりではなく、他の読取・インデックス等は別途確認する。実機・負荷測定で必要なら更新確認専用の軽いAPIを追加する。

### 来場者の送信状態

| 状態 | 表示と回復方法 |
|---|---|
| 初期読込 | レイアウトを保つ控えめなプレースホルダー。受付前に送信を有効にしない |
| 入力中 | 入力とテーマを保持。本文が空の場合は理由が分かる形で送信不可を示す |
| 送信中 | 即時に待機表示。入力・対象イベントの変更を一時抑制して送信内容を固定 |
| 長時間待機 | 3秒程度から「送信に時間がかかっています」。不明な進捗率は表示しない |
| 成功 | サーバー成功応答後に完了画面へ。成功した下書きだけを削除 |
| 応答不明・タイムアウト | 「送信結果を確認できませんでした」。同一requestId・同一内容で確認を兼ねて再試行 |
| 通信失敗・503 | 下書きを保持し「もう一度送る」。オフライン中は接続回復を案内 |
| 429 | サーバーの再送可能時刻を示し、それまで連打を抑制 |
| 受付終了 | 本文を保持して終了を案内。別イベントへ自動送信しない |
| 入力エラー | 該当項目に理由を表示し、必要に応じてフォーカスを移す |

本文・テーマ・eventIdと、送信開始時のrequestId・送信内容を、同一タブ内の復帰に使える `sessionStorage` にイベント単位で保存する案を検証する。保存できない環境では画面内の保持を優先し、リロード後の復元を約束しない。成功・明示的な破棄・期限切れで削除する。復元対象には短い有効期限（初期案2時間）を設ける。

応答不明の送信は、元の内容の再試行と、内容を変えた新規投稿を区別する。異なる内容に同じIDを使わず、元の結果が不明なまま新規投稿する場合は重複の可能性をその時点で伝える。接続復旧だけを理由に本文を自動送信しない。

## 8. 共有の設計

来場者は完了画面、運営は設定画面と共通ヘッダーの補助操作から共有できるようにする。入力途中に共有を主操作として競合させない。

- 対応環境：ボタンタップからOSの共有シートを開く。共有内容はイベント名、簡潔な案内、募集URL。
- 非対応・利用不可：同じ場所に「リンクをコピー」を用意。コピーも失敗した場合はURLを選択してコピーできるようにする。
- 共有キャンセル：失敗通知を出さず元画面に戻す。共有APIの完了をSNSへの投稿完了と断定しない。
- 運営用：会場で見せられるQR表示と、通常用／Instagram掲載用のリンクを用意する。QRには信頼できる募集URLだけを含める。
- 通常共有は `?event=<id>`、Instagram掲載用だけ `&from=instagram` を付ける。一般共有の生成時には元URLの流入パラメータを引き継がない。計測値はリンク由来であり、実際の共有先アプリの証明ではない。
- GitHub PagesのbasePath、URLエンコード、受付終了したリンクの着地を維持・検証する。

Web ShareはHTTPSとユーザー操作などの条件があり、環境ごとのフォールバックが必要。[MDN Web Share API](https://developer.mozilla.org/en-US/docs/Web/API/Web_Share_API)、[Navigator.share](https://developer.mozilla.org/en-US/docs/Web/API/Navigator/share)

イベントごとのSNSプレビュー画像は初期範囲に含めない。静的配信で `?event=` だけを変えても、イベントごとのプレビューを確実に生成できる設計にはならない。必要になった段階で専用URL・ビルド生成等を別途検討する。

## 9. 実装単位と依存関係

| 実装単位 | 主な対象 | 完了条件 |
|---|---|---|
| 基本スタイル・操作部品 | `app/globals.css`、`components/ui/button.tsx` 等 | パレット・余白・文字・押下・フォーカス・待機・reduced motionが揃う |
| 来場者フロー | `app/page.tsx`、投稿フォーム・完了表示の部品 | イベント判定→入力→完了の導線と全エラー状態が成立 |
| 再送・下書き | `lib/api-client.ts`、投稿状態を管理するhook | 応答消失後も同一IDで再試行。復帰後も対象と本文を混同しない |
| 運営の情報整理 | `app/admin/panel.tsx`、`app/admin/layout.tsx` | 質問が初期表示、集計・設定へ移動して戻れる |
| 更新・ページング | `lib/api-client.ts`、`server/src/report.ts`、関連テスト | cursor伝達、自動確認、重複排除、期限切れ復帰、スクロール維持 |
| イベント取得・編集 | 単一イベント取得とPATCHのクライアント接続 | 終了・404・障害の区別、version競合表示 |
| 共有 | `lib/public-url.ts`、共有操作・QR部品 | OS共有→コピー→URL表示の代替、一般流入とInstagramの区別 |
| 契約・文書 | `contracts/openapi.yaml`、既存ロードマップ | 実際のAPI変更だけ契約へ反映し、実装済み／予定の差を解消 |

既存のRadix系UI部品を活用し、CSSのtransform/opacity中心で試作する。新しいアニメーションライブラリは必要性が確認できるまで導入しない。グローバルなbutton・main・h1への指定は画面や部品に範囲を絞り、運営画面と来場者画面の意図しない干渉を減らす。

初期案の多くは既存APIで対応可能。リアルタイム専用APIや新たなDB項目は測定後の判断とし、UI刷新のためだけにデータ移行を発生させない。

## 10. 進め方

目安は実装担当1名＋デザイン確認・実機評価の協力者で、合計13〜19作業日（約3〜4週間）。協力者の募集待ちや本番基盤の修復は含まない。各工程の完了条件を満たしてから次へ進める。

| 工程 | 目安 | 成果物 | 次へ進む条件 |
|---|---:|---|---|
| D0 現状の基準測定 | 1〜2日 | 現行のスマホ画面記録、主要タスクの時間・迷い・誤操作、状態一覧 | 比較条件と主要な失敗箇所が明確 |
| D1 操作感とフローの試作 | 2〜3日 | ボタン・入力・送信・完了・シートの触れる試作、来場者／運営の構成案 | 片手操作、キーボード、動きを減らす設定で主要操作が自然 |
| D2 来場者フローの実装 | 3〜4日 | 入力中心の画面、イベント判定、下書き、冪等再送、状態表示 | 入力消失・二重送信・誤イベント送信の検証を通過 |
| D3 運営・共有の実装 | 4〜6日 | 質問中心の画面、自動更新、ページング、設定競合、共有・QR | 新着到着中も読書を継続でき、全件へ到達できる |
| D4 実機評価と仕上げ | 3〜4日 | 現行比較、改善記録、操作仕様の確定版、公開判定 | 以下の受入基準と既存の総合テストを通過 |

最初に作る試作は「ボタンを押す→送信中→完了」の1本と、「質問を読んでいる途中に新着が届く」の1本。静止画の見栄えだけで操作感を確定せず、この2本を実機で評価してから全画面へ展開する。

既存ロードマップの「既存デザインを維持」は、今回の要件では「既存カラー・機能・基盤を維持し、UI/UXを刷新」に置き換える方針。既存のP7総合テストに本書のD4を組み込み、基盤の受入条件も継続する。公開時は旧フロント成果物へ戻せるようにし、API変更がある場合は旧画面との互換性を確認する。

## 11. 受入基準と評価方法

数値は今回の提案値で、達成済みではない。小人数テストの割合を利用者全体の統計として扱わず、問題の発見と現行比較に使う。

| 観点 | 合格目標・確認方法 |
|---|---|
| 操作の即時性 | タップ開始から視覚反応まで100ms以内を目標に実機記録で確認。待機中も押した結果が分かる |
| 操作感 | 「押した手応え」「反応の速さ」「完了の確かさ」を各5段階で評価し、各中央値4以上。現行以下の項目は原因を確認 |
| 分かりやすさ | 初見の来場者5名が説明なしで、指定イベントへの投稿と完了確認を5名とも遂行できるまで重大な迷いを修正 |
| フローの短さ | イベント付きURLから本文入力まで、入口ボタン・モーダルを挟まない。入力開始までの中央値5秒以内を目標 |
| 効率 | 同じ質問文・同じ条件の現行比較で、本文を考える時間を除いた操作時間の中央値を20%以上短縮する目標 |
| 当日運用 | 運営3名程度で、新着が届いても読書位置・フォーカスが勝手に変わらない。新着認知→表示→過去質問へ移動が完結 |
| 更新速度 | 正常通信・前景表示で、保存から新着案内まで95%が5秒以内。会場相当の負荷・ネットワーク条件を記録 |
| 送信の確実性 | 保存後の応答消失、連打、再試行、復帰を含むテストで同一送信の重複保存0件、復元対象の下書き消失0件 |
| 共有 | 募集ページから共有開始まで2操作以内。OS共有非対応・拒否・キャンセル・コピー失敗からも行き止まりにしない |
| 一覧の完全性 | 51件以上と150件以上のデータで全件に到達でき、ページ境界に重複・欠落がない。新着検知とcursor失効も併用試験 |
| 表示・入力 | 320〜430 CSS px幅、横向き、キーボード表示、200%文字拡大で主操作と本文が隠れない。ダブルスクロールを避ける |
| アクセシビリティ | VoiceOver/TalkBack、キーボード、reduced motionで投稿・共有・運営主要操作を完了。フォーカスと状態通知を確認 |

主要な実機対象はiPhone Safari、Android Chrome、Instagramアプリ内ブラウザー。OS・ブラウザーのバージョンと端末を記録し、PC操作も回帰確認する。エミュレーターだけでキーボードと指の操作感を合格にしない。

通信試験は通常回線、会場相当の遅延、オフライン→復帰、401/403、429、503、受付終了の直前直後を含む。運営の複数端末編集、ブラウザーの戻る、共有シートからの復帰、イベント切替中の遅延応答も検証する。

技術検証は変更箇所に応じた状態遷移・API連携テスト、既存のサーバーテスト、静的ビルドを中心とする。色やCSS値をそのまま写したテストは増やさない。品質測定のログへ質問本文・認証トークンを含めない。

## 12. 今回決める方針と残る検証

計画の推奨方針は、入力を最初の画面に出すこと、黄色・黒・白を維持すること、押下と結果の反応を共通化すること、新着で読書を中断しないこと、共有を募集URLに限定することの5点。

残る検証は、押し込みの強さと時間、キーボード表示時の主ボタン位置、テーマ選択の初期値、自動更新の間隔と負荷、実機での共有対応。いずれもD1〜D4で結果を記録し、画面全体の方針から切り離して調整できる設計にする。

本書作成時点では、アプリのソース変更・デプロイ・利用者テストは行っていない。
