# 本番環境の構築：再設計案

更新日：2026-09-16。方式選定のための提案であり、新環境の構築・契約・移行は未実施。

## 1. 方針

**運用の容易さと信頼性を優先し、標準のNext.js＋Node.jsとPostgreSQLへ移行して、Renderでまとめて運用する案を第一候補とする。** 有料サービスの利用は可能。予算上限、負荷、許容停止時間は未確定のため、構成・契約プランの最終決定は見積もりと検証後に行う。

GitHubはソース保管・変更レビュー・自動検証に利用する。公開中のアプリがリクエストの処理にGitHubを必要とする設計にはしない。GitHubの変更と、実行基盤の変更は別の判断である。

ホスティングサービスを選ぶだけでは信頼性は担保できない。アプリの冗長化、DBの自動切り替え、誤操作からの復旧、外部監視、担当者の引き継ぎを一つの運用として設計する。

## 2. 現在の状態と課題

ローカルコードで確認できた内容：

- `package.json`はNext.jsを含むが、実際の起動・ビルドはvinext（`1.0.0-beta.5`）とCloudflare Workersを利用している。標準Next.jsとしての動作確認は別途必要。
- `lib/server.ts`、`lib/auth-db.ts`、`db/index.ts`、`lib/password-auth.ts`は`cloudflare:workers`に依存している。
- APIはD1の`prepare().bind()`、`batch()`、SQLiteのSQLを直接使用している。DB接続文字列だけの変更では移行できない。
- 匿名投稿は`cf-connecting-ip`がないと503を返す。移行先で信頼できる接続元IPの取得方法を実装する必要がある。
- 運営認証には同期版`scryptSync`を使用。無料WorkerのCPU制限に関する確認が旧案では未完了。Node.jsへの移行後も同時ログイン時の処理停滞を検証する。
- 現在のGitHub ActionsとデプロイスクリプトはCloudflare専用。

旧資料には「D1作成済み・Worker未公開・既存Sites公開版は別環境」と記載されている。今回はクラウドの実状態や保存データを照会していないため、移行前に再確認する。[旧案と従来手順](archive/本番環境の構築-Cloudflare旧案.md)は履歴として保存する。

## 3. 方式比較

以下の評価は、このアプリと少人数での保守を前提にした設計上の判断。各サービス全般の信頼性の順位ではない。

| 方式 | 運用の容易さ | 信頼性を高める方法・制約 | 移行負担 | 評価 |
|---|---|---|---|---|
| **Render＋Render Postgres** | アプリ・DB・ログ・復旧操作を同じサービスに集約 | 複数アプリインスタンス、DBのHA、自動バックアップ。単一リージョン全体の障害は残る | Next.jsの標準化、D1→PostgreSQL、IP処理の変更 | **第一候補**。管理対象を抑えつつ冗長化を組み込める |
| **Vercel＋Supabase** | Next.jsの公開・プレビューは扱いやすい。DBは別の管理画面 | DB復旧、接続数制御、両サービスの障害対応が必要。日次バックアップとPITRは別機能 | 同上。サーバーレス向けDB接続設計も必要 | 第二候補。プレビュー中心の開発やSupabaseの機能を活用する場合 |
| **Cloudflare Workers有料＋D1** | 既存コードを最も活用できる | CPU上限の緩和を検討できるが、実認証負荷・復旧の検証は必要 | 小。ただしvinext等の継続保守を評価 | 移行リスクを抑える比較対象として残す |
| **AWS等のマネージドアプリ基盤＋冗長DB** | 権限・ネットワーク・監視・課金の設計対象が増える | 詳細な冗長化・監査要件に対応する設計が可能 | 大。クラウド運用経験が必要 | 大学側に既存基盤と保守担当者がいる場合に再評価 |
| **VPS＋アプリ＋DBの自己管理** | OS更新・バックアップ・障害対応を自分たちで担当 | 一台構成は単一障害点。冗長化すると運用が複雑になる | 中〜大 | 今回の優先事項とは合いにくい |

RenderはNext.jsをNode.js Web Serviceとして公開でき、ヘルスチェックによる新バージョンへの切り替えと異常インスタンスの再起動を提供する。[Next.js公開](https://render.com/docs/deploy-nextjs-app)、[ヘルスチェック](https://render.com/docs/health-checks)

Render PostgresのHAは1 CPU以上などの条件があり、待機DBも課金対象。同じリージョン内の別ゾーンを利用する。非同期複製のため直近の書き込みが失われる可能性はあり、無停止・損失ゼロの保証ではない。[HAの条件と制約](https://render.com/docs/postgresql-high-availability)

Supabaseはプランに応じたバックアップを提供し、PITRは追加費用の対象。Vercelの有料プラン利用だけを根拠にサービス全体のSLAを保証しない。必要なら対象契約と除外条件を確認する。[Supabaseバックアップ](https://supabase.com/docs/guides/platform/backups)、[Vercel SLA](https://vercel.com/legal/sla)

Cloudflare有料化は現行のCPU問題への候補であり、無料枠での未検証をCloudflare全体の信頼性不足とは扱わない。[Workers制限](https://developers.cloudflare.com/workers/platform/limits/)

## 4. 推奨する構成

| 用途 | 構成案 |
|---|---|
| ソースと検証 | 団体所有の非公開GitHubリポジトリ。PRでテストとビルド |
| 本番アプリ | Renderの有料Node.js Web Service。ステートレスな2インスタンスを基本案とする |
| 本番DB | アプリと同一リージョンの有料Render Postgres。HAを有効化できる構成 |
| 確認環境 | 本番と分離したWeb Service・DB・秘密情報。架空データのみ |
| 認証 | 現在の運営ID・パスワード方式を維持。セッション・権限・制限カウンターを共有DBへ保存 |
| 公開URL | 団体所有の独自ドメインとHTTPS。移行先を変えてもURLを維持できるようにする |
| 監視 | 外部からの死活監視、投稿処理の失敗率、DB容量、接続数、通知先を設定 |
| データ保護 | PITRと、別の保護された保管先への定期エクスポート |

質問・セッション・添付ファイルなどをアプリのローカルディスクに永続保存しない。複数インスタンス間のNext.jsキャッシュ等の整合性も確認する。リージョンは日本からの実測遅延、提供機能、団体のデータ保管要件から選ぶ。

低価格の単一アプリ・単一DB構成は復旧可能な構成として比較できるが、上記の冗長構成と同等の可用性とは扱わない。リージョン全体の停止も許容できない場合は別途複数リージョン設計が必要となる。

## 5. 費用の決め方

無料枠の利用を本番設計の前提から外す。月額総額は次の内訳で見積もる。

- Render：ワークスペース料金＋アプリ2台＋DB本体とHA待機系＋DBストレージ＋確認環境＋帯域超過分。
- 共通：ドメイン更新費＋外部バックアップ保管＋監視＋税金。
- Vercel＋Supabase比較案：Vercelのプラン・利用席・従量課金＋Supabaseのプラン・各環境のCompute・PITR等。

最小プランの広告価格をそのまま本番全体の価格として提示しない。HA・確認環境・チーム権限を含む見積書にし、平常月とイベント開催月を分ける。料金アラートと支払い担当者を設定し、利用停止を伴う支出上限は可用性への影響も確認する。

公式料金は選定時に再確認する：[Render](https://render.com/pricing)、[Vercel](https://vercel.com/docs/plans/pro-plan)、[Supabase](https://supabase.com/pricing)。本資料では未確定の構成について確定月額を置かない。

## 6. 信頼性の受入条件

以下は検証用の目標案であり、達成済みの数値や事業者の保証ではない。利用人数・イベント日程を確認して確定する。

| 項目 | 目標案・確認方法 |
|---|---|
| 可用性 | 月間99.9%以上を目標に外部監視。特にイベント開催時間の停止を別に記録 |
| 障害検知 | 5分以内に運用担当へ通知。通知を受けた担当者と代行者を明確にする |
| データ復旧 | 目標復旧時間（RTO）60分以内、許容データ損失（RPO）15分以内をPITR復旧試験で確認 |
| 負荷 | 想定ピークを決め、その2倍で匿名投稿・管理画面・同時ログインを検証 |
| 権限 | 未ログイン・無効化済み担当者から質問や担当者情報を閲覧できない |
| 更新 | ヘルスチェック不合格の版へ切り替わらない。旧版へ戻す手順を確認 |
| 引き継ぎ | 主担当以外が手順書からログイン・デプロイ・復旧できる |

Renderの有料PostgresにはPITRがあり、保持期間はワークスペースプランにより異なる。直近10分以内の時点には復旧できないため、上記RPOは実測して判断する。DB復旧は新インスタンスの作成と接続先切り替えを含む。[復旧仕様](https://render.com/docs/postgresql-backups)

HAはインフラ障害への対策、PITRは誤削除や不正更新から戻す対策であり、両方を用意する。リージョン全体の障害や外部バックアップからの復旧については、別途達成可能なRTO/RPOを測定する。

## 7. 移行に必要な実装

1. **実行基盤**：vinext経由の起動を標準Next.jsへ変更。Node.jsの対応LTSを固定し、ビルド、Route Handlers、Cookie、動的ページを検証する。既存の`npm run build/start`は移行先用としてそのまま使えない。
2. **DB**：D1アクセスをPostgreSQL用データアクセス層へ集約。`?`プレースホルダー、`INSERT OR IGNORE`、`strftime`、`meta.changes`、`batch()`の原子性を置き換える。ミリ秒時刻の桁数、フラグの型、外部キー・ユニーク制約も検証する。
3. **認証**：Cloudflareの環境バインディングを移行先の秘密情報へ置換。既存scryptハッシュの互換性を維持し、非同期化等によるCPU負荷対策を検証。パスワード変更・担当者無効化によるセッション失効と初期オーナー作成を維持する。
4. **投稿制限**：移行先のプロキシ仕様に沿って信頼するIP情報を限定する。任意の`X-Forwarded-For`を無条件に信用しない。偽装ヘッダー、共有回線、複数アプリでの同時投稿を検証する。
5. **運用機能**：短いタイムアウト付きのDB疎通ヘルスチェック、秘密情報を出さないログ、失敗通知、DB接続プール・再接続を実装。書き込みの無条件再試行を避け、二重投稿への対策を検証する。
6. **公開手順**：Cloudflare専用CIを新構成へ置換。DB変更を一度だけ適用し、旧版と互換性のある追加変更を基本とする。確認済みコミットを本番へ反映する。

Supabase SDKが依存関係に含まれていても、現行の質問・認証DBがSupabaseへ移行済みという意味ではない。

## 8. 構築・切り替えの順序

1. 月額予算、同時利用者数・投稿数、イベント日時、データ保管要件、RTO/RPOを確定する。
2. 団体所有のアカウント、二要素認証、復旧手段、支払い担当、運用担当と代行者を登録する。
3. 確認環境を構築して前節の改修を行い、架空データで受入条件を検証する。
4. 本番のアプリ・DB・独自ドメイン・監視・バックアップを設定する。HA切り替えと空の別DBへの復元を試す。
5. 既存Sites版・D1・ローカルのどれに移行対象データがあるか確認する。新規開始か移行かを決定し、移行する場合は件数・イベントとの関連・日本語・日時・認証ハッシュを照合する。D1のSQLダンプをPostgreSQLへ直接投入しない。
6. 切り替え時に旧環境の受付を停止し、最終バックアップと移行を行う。セッションは原則失効して再ログインとし、パスワード再設定の要否は事前に確定する。
7. 新環境で匿名投稿、受付終了、管理画面、担当者権限、Instagram経由の分類、Secure Cookieを確認して公開先を切り替える。
8. 新環境で書き込みが始まる前なら旧環境へ戻せるようにする。書き込み開始後は単純にDNSを戻すとデータが分岐するため、受付停止・差分回収・整合性確認を含む戻し手順を用意する。
9. 定めた観察期間の後に旧環境の停止・データ保持・削除を判断する。移行完了までは旧資源を削除しない。

## 9. 日常運用

- 更新時：確認環境で検証 → 復旧可能性を確認 → DB変更 → 本番公開 → 投稿と認証を確認。イベント直前の機能追加は避ける。
- 障害時：通知を確認 → 必要に応じて受付停止 → アプリ障害かDB障害かを切り分ける。アプリのロールバックだけではDBは戻らない。
- データ破損時：新しいDBへPITR復元 → 件数・関連・権限を確認 → 接続先を変更 → 投稿・認証を確認 → 受付再開。
- バックアップ：PITRに加え、毎日および重要な変更前・イベント終了後に外部へエクスポートする。保存失敗を通知し、保持期間・閲覧権限・削除方針を決める。
- 定期確認：毎月の料金・容量・脆弱性対応、イベント前と四半期ごとの復旧訓練、担当者交代時の権限見直しを行う。

質問本文、パスワード、セッション、認証ハッシュ、DB接続情報を通常ログや公開CI成果物に出さない。バックアップは暗号化とアクセス制限のある団体管理の保管先へ置く。

## 10. 次に確定すること

有料利用と運用・信頼性の優先方針は確認済み。次は、月額上限とピーク負荷を確認し、Renderの冗長構成とVercel＋Supabaseの比較見積もりを作る。その後に方式を確定し、確認環境の移行実装へ進む。

本資料の更新では、アプリ・CI・既存クラウド資源の変更や新規契約は行っていない。
