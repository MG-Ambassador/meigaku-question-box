# 運営管理画面・共通UI改善計画

作成日：2026-09-26　追加更新日：2026-09-30　状態：計画（本書の機能は未実装）

[UIUX刷新計画](UIUX刷新計画.md)に対する追加計画。今回は計画書のみ更新し、アプリケーションの実装・データ操作・公開は行わない。

2026-09-30追記：ルーム形式・固有URL・紙飛行機による投稿を追加する。第10節が従来計画と異なる場合は第10節を優先する。

## 1. 目的と設計方針

質問を見分ける、テーマで整理する、後で読む質問を残す、集計から本文へ進む、終了イベントを整理する、という運営の一連の操作をつなぐ。既存の押下反応、入力保持、読書位置を動かさない新着通知、匿名投稿、運営認証を維持する。

以下は仕様の初期案。お気に入りの共有範囲や削除方式は依頼で指定されていないため、**担当者個人のお気に入り／復元可能な削除**を採用案とする。テーマ色は今回の追加要望として運営画面に限定して追加し、ブランドの黄色、主操作、来場者画面の色は維持する。

## 2. 現行実装で確認した点

- `event-workspace.tsx` は50件単位の一覧と集計を表示するが、テーマ条件・並び順・お気に入りは持たない。集計のテーマ・日付・流入元から質問へ移動できない。
- `report.ts` のcursorはイベント、sequenceの上限、集計時点等を保持する。条件付き一覧には条件を含むcursor設計が必要。
- イベントは `open` と `version` を持つが、アーカイブ・削除状態はない。既存POSTは更新もできるため、新しい状態制約をPATCHだけに追加すると迂回できてしまう。
- Switchのthumbは共通部品のTailwind `translate` と画面CSSの `transform: translateX(19px)` が併存する。二重移動の可能性があり、実描画で確認する。48×28pxの外枠に22pxのthumb、padding・borderも別指定されている。
- 設定画面の新規作成シートと既存設定が同時にマウントされるため、固定ID `event-accepting` の重複も解消対象とする。

## 3. 質問一覧：テーマ色・並び替え・お気に入り

### テーマの視覚識別

本文の読みやすさを優先し、カード全面の強い塗り分けを避ける。テーマラベル、細い左辺の線、集計バーに共通の色を使う。

| テーマ | 色の方向性（色値は試作で確定） | 併記する情報 |
|---|---|---|
| 大学生活 | 青 | テーマ名 |
| 学び・授業 | 青緑 | テーマ名 |
| 入試・進路 | 橙 | テーマ名 |
| 留学・国際交流 | 紫 | テーマ名 |
| その他 | グレー | テーマ名 |

色だけで区別させず、常にテーマ名を表示する。文字は既存の濃色を基本とし、選択・お気に入りの黄色とテーマ色の役割を分ける。通常文字のコントラスト4.5:1、操作の識別に必要な境界・フォーカス3:1を検証目標とする。

### 絞り込みと並び替えを分ける

一覧上部に「テーマ：すべて／5テーマ」「表示：すべて／お気に入り」「並び順：新しい順／古い順／テーマ順」を配置する。スマートフォンで常時表示する操作が多すぎる場合は、テーマチップと「絞り込み・並び順」シートへ整理し、適用中の条件は一覧上部に残す。

テーマ順は「大学生活→学び・授業→入試・進路→留学・国際交流→その他」の固定順、各テーマ内は新しい順。テーマ見出しで区切る。初期表示は現在と同じ新しい順。

- 取得済み50件だけをブラウザーで並べ替えない。全件を対象とするサーバー検索・ページングを実装する。
- 条件変更はcursorを破棄して先頭から取得する。新着が来ても自動挿入・自動並び替えをしない。
- イベント・テーマ・順序・お気に入り・日付・流入元をURLで表現する。質問本文、担当者ID、トークンはURLに入れない。
- 戻る操作では条件と読書位置を復元する。失効したcursorでは取得済み内容を残し、明示的な更新を案内する。
- 「該当0件」と通信失敗を分け、「条件を解除」を用意する。

### ワンタップのお気に入り

各質問の右上に48×48px以上の星ボタンを配置する。本文の閲覧・展開と別の操作領域にし、確認ダイアログを挟まない。`aria-pressed` と「お気に入りに追加／解除」の名前、塗り・輪郭で状態を伝える。

お気に入りはGoogle認証の `sub` に紐付く個人用とし、再ログイン・別端末でも復元する。画面にも「自分のお気に入り」と明示する。運営共通の選定リストは今回追加しない。

タップ直後に表示を切り替え、同じ質問への保存は直列化する。APIはtoggleではなく `{favorite: true/false}` の希望状態を送る冪等な操作とする。失敗時は戻して再試行を案内し、古い応答で新しい操作を上書きしない。お気に入り一覧で解除した項目は直ちに消して読書位置を動かさず、「解除済み・元に戻す」をその場に残し、次回更新で除外する。

## 4. 集計から本文への導線

| 集計でタップする場所 | 遷移先 |
|---|---|
| 質問総数 | 同じイベントの全質問 |
| テーマ名・件数・バーの行 | 該当テーマの質問 |
| Instagram等の流入元 | 該当流入元の質問 |
| 日別の行 | 日本時間の該当日の質問 |

行全体をボタン／リンクとして扱い、矢印と「質問を見る」で操作可能と示す。0件は空結果を説明する。遷移時には以前の質問条件をいったん置き換え、集計項目に対応する条件だけを適用する。

質問一覧で条件・件数を表示し、見出しへフォーカスを移す。「集計に戻る」とブラウザーの戻るで集計の位置を復元する。集計は複数質問のまとまりなので、まず該当一覧に進み、各本文を読めるフローにする。

集計から移動した間に投稿数が変わる場合は、一覧の取得時点を表示する。古い集計件数と新しい一覧件数が常に一致するとは見せない。総数と条件付き件数を別フィールドで扱う。

## 5. イベントのアーカイブ・削除

受付状態 `open` と整理状態 `active / archived / deleted` を分ける。

| 操作・状態 | 来場者 | 運営 | 戻し方 |
|---|---|---|---|
| 通常（active） | openに従って受付 | 通常一覧に表示 | — |
| アーカイブ | 受付終了。既存URLは終了案内 | 通常一覧から除外。「アーカイブ」で質問・集計・お気に入りを閲覧 | 通常に戻す。受付は閉じたまま |
| 削除（ごみ箱） | 一覧から除外。既存URLは利用できない案内 | 通常・アーカイブから除外。ごみ箱では最小限のイベント情報と復元操作 | アーカイブ状態へ復元。受付は閉じたまま |

設定末尾に「イベントを整理」を置き、アーカイブと削除を主操作から離す。確認にはイベント名と影響を明示する。「削除」は「ごみ箱へ移動し、復元できる」ことを説明する。初期版では自動消去・完全削除を実装せず、保存済み質問・集計・お気に入りを保持する。完全なデータ消去が必要な場合は保存期間と削除対象を決め、別の処理として設計する。

すべてversion照合と監査ログを伴う。アーカイブ／削除と `open=false` は同一トランザクションで更新する。古いPOST・PATCHから受付再開できないよう、全更新経路で状態遷移を検証する。新規投稿も同じイベント状態を確認する。受理済み投稿の同一requestIdによる再確認は既存の冪等性を維持する。

削除済みイベントの質問・集計・お気に入り取得をAPI側で拒否し、既存cursorも無効にする。表示中の別端末は次の取得で状態変化を通知し、一覧から離れる。公開APIでは監査情報や削除担当者を返さない。

来場者の入力・完了・イベント選択・使い方・共有、運営のログイン・質問・集計・設定・新規作成・確認シートを対象に、実際に使う共通部品を点検する。

| 対象 | 修正・確認内容 |
|---|---|

| ラベルと補足 | ラベル左・操作右を基本にし、長文・200%文字拡大では自然に折り返す。IDはインスタンスごとに一意にする |
| ボタン・星・更新・共有 | 48px以上の操作領域、押下・待機・無効・フォーカスの統一。アイコンの光学的な中心とラベルの整列 |
| 入力・テーマチップ・選択欄 | 高さ・余白・折返し・選択状態の統一。色変更後もラジオ操作とキーボード順を維持 |

受付Switchは現行どおり「イベントを保存」で反映する方式を維持し、「変更は保存すると反映されます」と表示する。未保存の切替を公開中の受付状態と混同させない。reduced motion時は移動・拡縮を止め、状態自体は明確に変化させる。

## 7. API・データ設計案

パス・フィールドの最終決定は実装開始時にOpenAPIと同時に確定する。

| 項目 | 変更案 |
|---|---|
| 質問取得 | 既存 `GET /api/admin` にcategory、sort、favorite、day、sourceを追加。未指定は既存挙動。全体集計と `filteredTotal` を分離 |
| cursor | 検索条件、順序、watermark、最後の複合キー、schema版を署名対象にする。個人のお気に入り検索は認証subにも紐付け、条件の違うcursorを拒否 |
| お気に入り更新 | `PUT /api/admin/questions/{id}/favorite`、希望状態をbodyに指定。subはトークンから決定。質問・イベントの存在と閲覧可否を確認 |
| 個人お気に入り | 認証sub配下の質問IDをキーに保存。eventId、category、dayJst、source、sequenceを検索用に保持し、本文は複製しない。取得後に元質問を読む |
| イベント整理 | version付きの専用状態変更API。archive／restore／trashを明示し、許可された遷移のみ受理。ごみ箱からの復元先はarchived |
| 管理イベント一覧 | 通常／アーカイブ／ごみ箱の条件を追加。公開一覧はactiveかつopenのみ |
| 既存データ | lifecycle未設定をactiveとして互換読込し、既存イベントを補完してから状態インデックス検索へ移行 |

テーマ順の検索用に `categoryOrder` を質問へ追加し、既存質問をdry-run付きで補完する。テーマ内はsequence降順とし、cursorはcategoryOrderとsequenceの両方を保持する。必要なFirestore複合インデックスを検索組み合わせ表から列挙して追加する。全質問取得後のクライアント側ソートや、全件走査による毎回の件数計算は採用しない。

お気に入りの追加・解除は投稿のwatermarkだけでは固定できない。個人のfavoriteRevisionを更新し、お気に入り検索cursorに含める。途中で集合が変わった場合はcursorを失効させ、表示済み本文を残して更新を案内する。フィルター中の新着通知は該当条件に合う投稿だけを数え、お気に入り集合の変更通知とは分ける。

状態変更時は `eventStats.dataVersion` も更新し、既存一覧cursorを失効させる。お気に入りの更新は個人側の版を使い、他の運営者の通常一覧を失効させない。組み合わせ条件の件数・新着検知の読取コストを測定し、3秒ポーリングで不要な集計読取を繰り返さない。

## 9. 受入基準

- 全5テーマをラベルと色で識別でき、色が判別できなくても内容と選択状態が分かる。
- テーマ順・新旧順・各条件の組み合わせで、150件以上の未読込分を含めて正しく取得できる。新着到着中も読書位置が維持される。
- 星は1タップで反応し、再ログイン・別端末で保持される。他の担当者のお気に入りには影響しない。連打・失敗・応答逆転・401／403を検証する。
- 集計のテーマ・日付・流入元から、条件に合う質問本文へ進める。戻る操作で集計の位置を復元する。
- アーカイブ／削除直後に新規投稿できず、古いPOST・PATCHでも再開できない。競合時は上書きしない。復元しても自動で受付を再開しない。
- ごみ箱の質問は通常APIから参照できず、復元後は質問・集計・お気に入りが戻る。削除中の再送は受理済み判定を壊さない。
- Switchは両端でthumbが収まり、ラベルから正しいインスタンスを操作できる。320／390／430px、横向き、200%文字拡大で主要操作が隠れない。
- すべての主要フローをキーボードとreduced motionで操作できる。iPhone Safari・Android Chromeで押下感、OSキーボード、VoiceOver／TalkBackを別途確認する。
- 既存の状態・ブラウザー・サーバー・移行テストを維持し、新機能の認可・状態遷移・ページ境界テストを追加する。型検査・静的ビルドを通過する。

実装後の合否は実測で記録する。本書作成時点では、新機能の試験・実機確認を実施していない。


## 10. 追加要件：ルームと紙飛行機による投稿（2026-09-30）

### 10.1 ルームを管理の単位にする

1つのイベントに1つのルームを対応させる。ルームが、イベント名・開催情報・受付状態・質問・集計・個人のお気に入り・募集URLをまとめて持つ。画面上は「ルームを作成」「ルームの設定」「ルームをアーカイブ」などに統一する。既存のイベントは同じIDのルームとして引き継ぎ、投稿済み質問との紐付けを保つ。API／Firestoreの内部名 `eventId` は互換性のため当面維持し、表示名変更だけを理由に全データを移行しない。

運営の入口をルーム一覧とし、「通常／アーカイブ／ごみ箱」を切り替える。各ルームにタイトル・開催情報・受付状態・質問件数・共有操作を表示し、ルームを開くと「質問／集計／設定」に進む。別ルームへの移動は運営画面だけで提供する。

アーカイブ・削除・復元は第5節の状態遷移をルームに適用する。削除はごみ箱への移動、復元先はアーカイブ、アーカイブ解除後も受付は停止したままとする。URL、質問、集計、お気に入りは保持し、完全削除・自動消去は初期範囲に含めない。権限は既存の認証済み運営者全員を維持し、ルームごとの招待・所有者権限は今回追加しない。

### 10.2 固有URLから直接そのルームへ入る

参加者の導線を「ルームURL／QR → 対象ルームの質問入力」に一本化する。ルーム名と開催情報は必ず表示するが、参加者向けのイベント一覧・変更ボタンは廃止する。URL指定なしの場合も勝手にルームを選ばず、「主催者から案内されたリンクまたはQRコードを開いてください」と案内する。

現行はGitHub Pagesへの静的出力であるため、初期実装の正規URLは `/<basePath>/?room=<固有ID>` とする。これなら作成直後のルームでも再ビルドなしにアクセスできる。固有IDは既存イベントIDを引き継ぎ、新規ルームにはサーバー側で一意性を保証したIDを発行する。タイトルを変更してもURLを変えず、削除後もIDを別ルームに再利用しない。任意の短いURL名の編集は初期範囲に含めない。

既存の `?event=<id>` は互換入口として残し、同じルームを開いて正規URLへ履歴置換する。roomとeventが両方あり異なる場合は曖昧なリンクとして案内し、別ルームへ送信しない。Instagram掲載用だけ `from=instagram` を付ける。共有・コピー・QRは新しい正規URLに統一する。

- アーカイブ／受付停止：同じルームで受付終了を表示。入力済み本文は保持する。
- ごみ箱／存在しないID：利用できないリンクと表示し、他ルームを紹介・自動選択しない。
- 復元：元のURLが再び同じルームを指す。復元だけでは投稿を再開しない。
- URLは参加者向けの公開入口であり、運営の認証を代替する秘密鍵として扱わない。
- `/rooms/<slug>/` のようなパス形式が必要になった場合は、静的配信の動的ルート解決を別途設計する。初期版で存在しないパスを生成しない。

### 10.3 紙に書き、折って、上へ送る投稿体験

中心の入力面を紙として表現し、質問本文とテーマを入力する。入力中に勝手に折り畳まず、明示的な「紙飛行機にする」で送信準備へ移る。この時点では投稿しない。

1. **書く**：紙面に本文を入力する。テーマ、文字数、匿名性・紹介についての説明を従来どおり提供する。
2. **折る**：「紙飛行機にする」で入力を検証し、キーボードを閉じ、内容のある紙面が折り畳まれる短いアニメーションを表示する。テーマと本文の確認手段、「書き直す」を残す。
3. **送る準備**：紙飛行機と「上にスワイプして送信」を表示する。指に追従して紙飛行機が上へ動き、送信できる位置に達すると文言・輪郭で知らせる。
4. **指を離す**：十分に上へ動かして離した場合だけ送信を確定する。飛行機は上方向へ飛び、同時に通信を開始する。動きの終了を待って通信を遅らせない。
5. **待機と完了**：飛び立つ動作は送信開始の表現とし、API成功前に「受け付けました」と表示しない。成功後に完了画面を表示して見出しへフォーカスする。

「書く→折る→上へ送る」を主体験とする一方、飛行機の下に「タップして送信」を常に用意する。キーボードのEnter／Space、読み上げ、スワイプが難しい人でも同じ結果を得られるようにする。本文入力中のEnterや日本語IME確定では送信しない。

### 10.4 ジェスチャーと動きの開始仕様

以下の数値は試作値であり、実機評価で確定する。

| 動作 | 初期仕様 |
|---|---|
| 折り畳み | 300〜450ms程度。紙面→折り目→飛行機の連続性を見せ、完了後に操作可能にする |
| 指への追従 | ドラッグ中は追従を遅らせるtransitionを使わない。主にtransformで動かす |
| 送信しきい値 | 上方向80 CSS pxを開始値とし、縦移動が横移動の1.5倍以上の場合に有効。速度だけでは送らない |
| 確定 | 有効なしきい値を超えてpointerupした時点。越えてから戻した場合は確定しない |
| キャンセル | しきい値未満、横／下移動、pointercancel、画面非表示、複数指は送信せず戻す。戻りは140〜180ms程度 |
| 飛行 | 上向き240〜360ms程度。完了の人工的な待機は入れない |
| reduced motion | 折り畳み・追従・飛行の移動を省略し、静止した紙／飛行機と状態文言で切替。タップ送信を利用できる |

ジェスチャー取得は送信準備中の専用領域だけに限定し、入力画面・ページ全体のスクロール、ブラウザーの戻る、ピンチ拡大を妨げない。領域の高さ、画面端との距離、safe areaを考慮し、短い画面では送信代替ボタンまで無理なく見えることを優先する。入力文字を飛行中の小さな面で読ませず、送信前には元の内容を確認できるようにする。

実装はReactの明示的な状態管理、Pointer Events、CSS／SVGを基本とする。紙の表裏・折り目を分け、必要なら装飾用の本文表示を複製するが、読み上げ対象は元の本文に一本化する。新しいアニメーション依存の採用は試作で必要性を確認してから判断する。

### 10.5 送信の確実性と状態管理

状態は `入力 → 折り畳み → 送信準備 → ドラッグ → 通信中 → 完了／結果不明` として分ける。書き直しは送信準備から入力へ戻し、本文・テーマを保持する。イベントではなくルーム単位の下書きとして既存保存方式を引き継ぐ。

requestIdは折り畳み開始時ではなく、スワイプ確定またはタップ送信時に作成し、ルームID・本文・テーマとともに通信前に保存する。二つの送信操作は同じ排他処理を使う。受付状態を確認し、オフラインなら送信せず準備状態を保持する。最終可否はサーバー判定に従う。

応答不明の場合は「もう一度飛ばす」ではなく「同じ内容で送信結果を確認」と表示し、既存requestIdと固定内容で再試行する。成功したか不明な紙飛行機を未投稿として戻さない。429、受付終了、503、画面離脱からの復帰でも本文を消さず、接続復旧だけで自動投稿しない。送信中に別ルームへ移動した場合の古い応答が新しい下書きを消さない既存の保護も維持する。

### 10.6 既存計画の変更と実装順

元のUIUX計画第4節の参加者向けイベント選択、第5節の主な送信操作はこの節で置き換える。操作は「折る」が増えるため、従来の操作時間20%短縮目標の達成を当然視しない。直接入力・直接送信の旧版と比較して、気持ちよさに加え、初見での成功率・時間・誤送信を測定する。

1. P0の共通UI修正と並行して、ルームURL・既存リンク互換の仕様を確定する。
2. 紙→折り畳み→スワイプ→待機→完了と、キャンセル・結果不明の触れる試作を作る。
3. iPhone／Androidでスクロール競合・片手操作・初見の理解を確認し、しきい値と動きの時間を調整する。
4. P1の状態管理・APIにルームのライフサイクルを反映し、P2〜P4の運営機能をルーム単位で実装する。
5. 来場者の選択UIを除き、正規URL・共有・QR・下書き・冪等送信と試作を接続する。
6. P5で既存機能と追加フローを総合検証する。

### 10.7 追加受入基準

- 新規ルーム作成直後、再ビルドなしで固有URL／QRから直接投稿画面へ入れる。参加者はルーム選択を求められない。
- タイトル変更・アーカイブ・ごみ箱・復元を経てもIDとURLの対応が変わらない。旧eventリンク、basePath、Instagram計測も正しく扱う。
- ルーム指定なし・不存在・ごみ箱・受付停止で、別ルームへ自動送信されない。
- 折っただけでは投稿されず、有効な上スワイプを離した時または送信ボタンだけで確定する。下・横・短い移動、pointercancel、複数指、連打で誤送信・二重送信がない。
- 指への追従、送信開始、サーバー受付完了の違いが分かる。通信遅延・応答消失・429・受付終了時も本文と再送IDを維持する。
- キーボード・読み上げ・reduced motionでもスワイプなしに投稿を完了できる。200%文字拡大と短い画面で本文確認・書き直し・送信が隠れない。
- 実機の初見利用者5名が口頭説明なしに投稿・完了確認を遂行できるまで重大な迷いを修正する。操作感の各評価中央値4/5以上を目標にし、誤送信0件を確認する。

追加仕様も計画段階であり、紙飛行機の操作感・実機性能・アクセシビリティは未検証。
